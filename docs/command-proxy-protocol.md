# Протокол Command Proxy v2

## Статус и назначение документа

Этот документ — контракт между PHP-агентом (`agentmodule`) и внешним
сервисом **Command Proxy**, который исполняет shell-команды от имени
агента. Реализация Command Proxy находится за пределами этого репозитория
и здесь не описывается — только протокол, которому она обязана
соответствовать.

Документ расширяет уже существующий (реализованный и используемый
сегодня) action `exec` тремя новыми: `start`, `wait`/`peek`, `kill` —
для поддержки асинхронных/фоновых команд со стороны PHP-инструментов
`terminal-start`, `terminal-wait`, `terminal-peek`, `terminal-kill`
(см. `app/src/Application/Tools/Terminal/`).

## Обзор

- **Транспорт**: Unix domain socket, путь берётся из переменной окружения
  `COMMAND_PROXY_SOCKET`.
- **Один запрос = одно соединение.** Клиент подключается, пишет один JSON
  объект (без завершающего `\n` со стороны клиента — сервер должен уметь
  прочитать один JSON-документ независимо от наличия разделителя), читает
  один JSON объект ответа как одну строку (`\n`-terminated), закрывает
  соединение. Сервер не должен держать соединение открытым после ответа.
- **Формат запроса**: JSON-объект с обязательным полем `action` (строка) и
  дополнительными полями, специфичными для action.
- **Формат успешного ответа**: JSON-объект, специфичный для action (см.
  ниже), без поля `error`.
- **Формат ответа с ошибкой**: JSON-объект вида
  `{"error": "<код>", "message": "<человекочитаемое описание>"}`. Поле
  `error` обязано быть одним из кодов из раздела [Коды ошибок](#коды-ошибок).
- Сервер обязан отвечать в пределах разумного времени даже на невалидный
  запрос — клиент всегда открывает соединение с коротким timeout на
  подключение (~2s) и настраиваемым timeout на чтение ответа.

## Actions

### `exec` (существующий, не меняется)

Синхронно исполняет команду и ждёт её завершения.

**Запрос:**
```json
{"action": "exec", "command": "npm test"}
```

**Успешный ответ:**
```json
{"stdout": "...", "stderr": "...", "exit_code": 0}
```

**Ответ с ошибкой:** `{"error": "..."}` (плоский формат уже в проде —
см. `Run.php::executeViaSocket()`; новые actions используют формат
`{"error": "<код>", "message": "..."}` из раздела выше, `exec` трогать не
нужно).

---

### `start`

Запускает команду в фоне и немедленно возвращает управление, не дожидаясь
завершения. Сервер обязан хранить job (процесс + накопленные буферы
stdout/stderr + статус) как минимум до его завершения и последующего
опроса, привязанным к `job_id`.

**Запрос:**

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `action` | string | да | `"start"` |
| `command` | string | да | Команда для исполнения |
| `cwd` | string | нет | Рабочая директория |
| `env` | object&lt;string,string&gt; | нет | Дополнительные переменные окружения |
| `max_lifetime` | integer (сек) | нет, default `600` | См. ниже |

**`max_lifetime` — обязательная серверная гарантия.** Сервер обязан
принудительно завершить (`SIGKILL`) процесс по истечении `max_lifetime`
секунд с момента запуска, **независимо от того, вызывал ли клиент
`wait`/`peek`/`kill` вообще**. Это единственная защита от утечки
процессов, если агент разорвал соединение/упал/забыл про job. Сервер
обязан клэмпить запрошенное значение до хард-капа (рекомендуется
`3600`) и не позволять `max_lifetime <= 0`.

**Успешный ответ:**
```json
{"job_id": "0f3e2b7a-4c1d-4b8a-9e2f-6d1a2b3c4d5e"}
```

**Ошибки:** `invalid_params` (нет `command`), `proxy_busy` (см.
[Коды ошибок](#коды-ошибок)).

---

### `wait`

Блокирующий опрос job: ждёт, пока job не завершится, либо пока не истечёт
`timeout`, — в любом случае возвращает текущий статус и **дельту** вывода
с указанных offset'ов (данные, накопленные со времени последнего
прочитанного клиентом байта).

**Запрос:**

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `action` | string | да | `"wait"` |
| `job_id` | string | да | Идентификатор job, полученный от `start` |
| `timeout` | integer (сек) | нет, default `15` | Сколько максимум ждать завершения job. **Сервер обязан клэмпить до хард-капа `30`** независимо от запрошенного значения — иначе клиент (PHP-агент) блокируется на непредсказуемо долгое время и теряет возможность вовремя среагировать на внешний сигнал отмены задачи. |
| `stdout_offset` | integer | нет, default `0` | Байтовый offset в stdout-буфере job, с которого вернуть дельту |
| `stderr_offset` | integer | нет, default `0` | Аналогично для stderr |

**Успешный ответ:**
```json
{
  "job_id": "0f3e2b7a-4c1d-4b8a-9e2f-6d1a2b3c4d5e",
  "status": "running",
  "exit_code": null,
  "stdout_delta": "...",
  "stdout_offset": 1024,
  "stderr_delta": "",
  "stderr_offset": 0,
  "truncated": false
}
```

`status` — одно из: `"running"`, `"exited"`. Если `"exited"` — `exit_code`
обязан быть целым числом (не `null`). Возврат по таймауту с job всё ещё в
статусе `"running"` — штатный, не ошибочный исход.

`stdout_offset`/`stderr_offset` в ответе — новые offset'ы, которые клиент
обязан передать в следующем вызове `wait`/`peek` по этому `job_id`, чтобы
не получать уже прочитанные данные повторно.

`truncated` — `true`, если серверный буфер для этого потока переполнился
и часть старых данных между переданным offset'ом и текущим началом
буфера была отброшена (см. [Лимиты буферов](#лимиты-буферов)).

**Ошибки:** `job_not_found`, `invalid_params`.

---

### `peek`

То же самое, что `wait`, но неблокирующее: возвращает текущее состояние
немедленно, без ожидания. Поле `timeout` не принимается (игнорируется,
если передано).

**Запрос:**
```json
{"action": "peek", "job_id": "...", "stdout_offset": 0, "stderr_offset": 0}
```

**Ответ:** идентичен по форме ответу `wait`.

**Ошибки:** `job_not_found`, `invalid_params`.

---

### `kill`

Принудительно завершает job.

**Запрос:**

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `action` | string | да | `"kill"` |
| `job_id` | string | да | Идентификатор job |
| `signal` | string | нет, default `"TERM"` | `"TERM"` или `"KILL"` |

**Успешный ответ:**
```json
{"job_id": "0f3e2b7a-4c1d-4b8a-9e2f-6d1a2b3c4d5e", "status": "killed", "exit_code": null}
```

Если job уже завершился к моменту вызова `kill` — это **не ошибка**:
`status` возвращается как `"already_exited"`, `exit_code` — реальный код
завершения процесса.

**Ошибки:** `job_not_found`, `invalid_params`.

---

## Лимиты буферов

Сервер обязан ограничивать размер накопленных stdout/stderr буферов на
job (по аналогии с `max_output` у `exec`, рекомендуется тот же порядок —
десятки/сотни KB на поток). При переполнении сервер обязан отбрасывать
**старые** данные (не новые) и выставлять `truncated: true` в следующем
ответе `wait`/`peek`, где это затронуло запрошенный диапазон — job при
этом не должен падать или прерываться.

## Коды ошибок

| Код | Когда возвращается |
|---|---|
| `invalid_action` | Значение `action` не входит в поддерживаемый набор |
| `invalid_params` | Отсутствует обязательное поле или оно некорректного типа/значения |
| `job_not_found` | `job_id` не существует или уже был вычищен сервером (job'ы после завершения обязаны храниться какое-то разумное время, чтобы финальный `wait`/`peek` успел забрать последние данные, прежде чем удаляться) |
| `proxy_busy` | Сервер временно не может принять новый `start` (например, достигнут лимит одновременных job) |

Формат ответа с ошибкой везде одинаковый:
```json
{"error": "job_not_found", "message": "Job 0f3e2b7a-... not found"}
```
